# 787. Cheapest Flights Within K Stops

**Сложность:** Medium  
**Источник:** [LeetCode](https://leetcode.com/problems/cheapest-flights-within-k-stops/)  
**Темы:** Graph, Bellman-Ford, DFS, DP

## Описание

Дано `n` городов и рейсы `flights[i] = [from, to, price]` — **направленные** рёбра. Даны `src`, `dst`, `k` — максимум **промежуточных остановок**.

Вернуть минимальную стоимость перелёта из `src` в `dst` не более чем с `k` остановками. Если невозможно — `-1`.

**Ключевое:** путь может быть дешевле, но **не влезать** в ограничение остановок.

```
n = 4, flights = [[0,1,100],[1,2,100],[2,0,100],[1,3,600],[2,3,200]]
src = 0, dst = 3, k = 1
```

- `0→1→3` — 1 остановка, цена `700` ✓
- `0→1→2→3` — 2 остановки, цена `400` ✗ (не влезает)

Ответ **`700`**, хотя есть путь дешевле `400`.

## Почему Дейкстра не работает

Дейкстра жадная: берёт узел с минимальным расстоянием и считает его **окончательным**. Здесь так нельзя — короткий путь может нарушать лимит остановок, и откатить это Дейкстра не умеет.

Отсюда низкий acceptance rate (~43%): решение с `PriorityQueue` проходит большинство тестов и падает на кейсе с ограничением.

## Реализация 1: Bellman-Ford (`bellman/BellmanFordSolution.java`)

```
dist[src] = 0, остальные = ∞
повторить (k+1) раз:
    next = копия dist
    для каждого ребра (u, v, w):
        если dist[u] != ∞ и dist[u] + w < next[v]:
            next[v] = dist[u] + w
    dist = next
```

**Проход `i` даёт лучшие пути ровно из `i` рёбер.** `k` остановок = `k+1` рёбер, отсюда число проходов.

**Почему нужна копия:** если обновлять на месте, внутри одного прохода можно использовать только что записанное значение — и «путь из `i` рёбер» превратится в «путь из `i` или больше рёбер». На `k = 0` это даёт неверный ответ.

**Проверка `dist[u] != ∞`** нужна, чтобы `MAX_VALUE + w` не переполнилось.

- **Время:** `O(k · E)`
- **Память:** `O(V)`

## Реализация 2: DFS с мемоизацией (`dfs/DfsSolution.java`)

Рекурсивный обход от `src` с отсечениями:
- `cur >= res` — текущий путь уже не дешевле найденного;
- `visited` — карта `город → (остаток k → лучшая цена)`.

**Мемоизация должна хранить по одному значению на каждую пару `(город, k)`** — вложенная карта обновляется, а не заменяется:

```java
if (v == null) {
    v = new HashMap<>();
    visited.put(src, v);      // создаём ОДИН раз
}
v.put(k, cur);                // и дописываем состояния
```

Если создавать новый `HashMap` на каждом шаге, старые состояния теряются — мемоизация перестаёт работать (но ответ остаётся верным, просто медленнее).

- **Время:** зависит от порядка обхода, в худшем экспоненциально
- **Память:** `O(V · k)` на мемоизацию

## Сравнение

| | DFS | Bellman-Ford |
|---|---|---|
| Строк | ~50 | **~20** |
| Проходов | зависит от данных | **ровно `k+1`** |
| Сложность | трудно назвать | **`O(k · E)`** |
| Мемоизация | `HashMap` руками | не нужна |

Bellman-Ford лучше: сложность гарантирована, а состояния разделены по слоям **структурно**, а не через отсечения.

## Ошибки при решении

| Ошибка | Причина |
|---|---|
| `visited.put(src, new HashMap<>())` на каждом шаге | новый `HashMap` затирал старые состояния — мемоизация не работала |
| `... < cur[1]` в Bellman-Ford | сравнивал с **номером города**, а не с `next[cur[1]]` (ценой) |
| `visited` и `res` — поля класса | состояние живёт дольше вызова; тесты создают `new Solution()` на каждый вызов |

**Урок:** сломанная оптимизация проходит все тесты, потому что тесты проверяют **ответ**, а не внутреннее состояние. Это второй такой случай за неделю (первый — `union by size` в MST).
