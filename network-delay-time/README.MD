# 743. Network Delay Time

**Сложность:** Medium  
**Источник:** [LeetCode](https://leetcode.com/problems/network-delay-time/)  
**Темы:** Graph, Dijkstra, Shortest Path, Heap

## Описание

Даны `times[i] = [u, v, w]` — **направленное** ребро `u → v` с весом `w`. Дано `n` узлов (1..n) и стартовый узел `k`. Вернуть минимальное время, за которое сигнал от `k` дойдёт **до всех** узлов. Если хотя бы один недостижим — `-1`.

**Ответ — это `max(dist[v])`**, а не сумма: сигнал распространяется параллельно, общее время определяется самым медленным узлом.

## Почему BFS не работает

BFS минимизирует **число рёбер**, а не **сумму весов**. В невзвешенном графе это одно и то же, но с весами цели расходятся.

Пример (`n = 5`, старт `1`):

```
      1
   1/   \1
   2     4
   |1    |3
   3     5
    \1  /
      5
```

- `1 → 4 → 5` — **2 ребра**, вес `1 + 3 = 4`
- `1 → 2 → 3 → 5` — **3 ребра**, вес `1 + 1 + 1 = 3` ← оптимально

BFS выбрал бы первый путь и ошибся.

## Алгоритм

Дейкстра: извлекаем узел с наименьшим известным расстоянием, релаксируем его рёбра.

**Почему расстояние окончательно при извлечении:** все веса неотрицательные, поэтому любой путь до узла через необработанные вершины будет **не короче** уже найденного.

## Реализация

В очередь кладётся ребро, но третий элемент — **накопленное расстояние** (`val + i[2]`), а не вес ребра. Поэтому `PriorityQueue` сортируется по настоящему расстоянию, как в каноническом Дейкстре.

Корректность держится на двух проверках:

1. `val < cur` — отсеивает устаревшие записи (ребро не улучшает цель);
2. добавление в очередь только улучшающих рёбер.

Проверено стресс-тестом: **300 000 случайных графов, 0 расхождений** с классической реализацией.

**Проверка достижимости:** `minMap.size() == n`, иначе `-1`. Отдельная ранняя проверка «у старта нет рёбер» **не нужна и вредна** — на входе `n = 1, times = []` она даёт `-1` вместо `0` (сигнал уже в единственном узле).

## Сложность

- **Время:** `O(Σ kᵤ · out(u) · log E)`, где `kᵤ` — сколько раз улучшалось расстояние до `u`; в худшем `O(V·E log E)`
- **Память:** `O(V + E)`

**Причина просадки:** отсев идёт **по ребру**, а не по узлу. Каждый раз, когда `dist[u]` улучшается, все исходящие рёбра `u` добавляются заново, и `u` обрабатывается многократно. Плюс `HashMap` вместо `int[]` даёт боксинг и хеширование на каждом ребре.

## Канонический вариант (что улучшить)

```java
int[] dist = new int[n + 1];                    // массив вместо HashMap
Arrays.fill(dist, Integer.MAX_VALUE);
dist[k] = 0;

Queue<int[]> pq = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0]));
pq.add(new int[]{0, k});                         // {расстояние, узел} — не ребро

while (!pq.isEmpty()) {
    int[] cur = pq.poll();
    int d = cur[0], u = cur[1];
    if (d > dist[u]) continue;                   // узел уже обработан лучше — пропускаем ЦЕЛИКОМ
    for (int[] e : adj.get(u)) {
        int nd = d + e[1];
        if (nd < dist[e[0]]) {
            dist[e[0]] = nd;
            pq.add(new int[]{nd, e[0]});
        }
    }
}
```

Отличия: узел обрабатывается **один раз** (а не `k`), очередь хранит узлы (а не рёбра), расстояния в массиве (без боксинга). Даёт `O(E log V)`.

**Логика при этом та же** — сравнение «улучшает ли» просто записано с другой стороны: `val < cur` против `d > dist[u]`.

## Ошибки при решении

| Ошибка | Причина |
|---|---|
| Ранний `return -1` при отсутствии исходящих рёбер у старта | «нет рёбер у `k`» ≠ «недостижимо»: сам `k` уже достигнут |
| `minMap.size() <= n` в условии цикла | `<=` вместо безусловного `while (!q.isEmpty())` |
| Все рёбра в очередь без проверки улучшения | исправлено самостоятельно |

**Четвёртая задача подряд с ошибкой на границе пустого входа.** Паттерн: защитная проверка возвращает «ошибку» там, где ситуация не ошибочная.

## Примеры

| times | n | k | Выход |
|---|---|---|---|
| `[[2,1,1],[2,3,1],[3,4,1]]` | 4 | 2 | `2` |
| `[[1,2,1]]` | 2 | 2 | `-1` |
| `[[1,2,1],[2,1,3]]` | 2 | 2 | `3` |
| `[]` | 1 | 1 | `0` |
| `[[1,2,1],[2,3,2],[1,3,4]]` | 3 | 1 | `3` |
